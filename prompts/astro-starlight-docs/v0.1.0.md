> **This prompt builds the developer documentation site AND consolidates the Quarto bound report into it.**
>
> Unlike the earlier `mintlify-component-docs` prompt (which kept Quarto strictly separate), this prompt's design decision — locked in by the maintainer — is to **embed the Quarto-rendered report under `/report/` on the new Astro Starlight site** and **retire the existing standalone Cloudflare Pages deploy** (`.github/workflows/deploy.yml`).
>

> If at any point during this work you find yourself editing `_quarto.yml`, `index.qmd`, any file under `notebooks/`, any analysis-stage code under `src/forensics/analysis/`, or `config.toml`, **stop and surface the question** in the HANDOFF block. Those surfaces are out of scope.

## Mission

Stand up [Astro Starlight](https://starlight.astro.build) as the unified documentation site for the `mediaite-ghostink` software. Produce a `website/` directory at the repo root containing a Starlight project that:

- Sources its content at build time from canonical `docs/` markdown (operator docs + ADRs) and from auto-generated CLI reference markdown.
- Embeds the Quarto-rendered forensic report at `/report/` as static assets, populated by `quarto render` running inside the deploy workflow.
- Builds and deploys to **GitHub Pages** on every push to `main` whose paths touch documentation, the CLI surface, the Quarto sources, or the website itself.
- Replaces (deletes) the existing `.github/workflows/deploy.yml` Cloudflare Pages deploy. The Cloudflare project becomes orphaned and is retired by the maintainer outside CI.

The final result is one URL — `https://abstract-data.github.io/mediaite-ghostink/` — that serves operator docs, ADRs, CLI reference, and the embedded Quarto report.

- The repo is `mediaite-ghostink`, a Python 3.13 + uv-managed forensic pipeline. GitHub owner: `Abstract-Data`.

- The Quarto book renders to `data/reports/` (per `_quarto.yml`'s `output-dir`). The new workflow must override this to render directly into `website/public/report/`.
- The CLI is a Typer app entered at `src/forensics/cli/__init__.py:main`. CLI documentation is auto-generated by walking the Typer app and writing markdown into `docs/cli/`.
- The repo currently has 7 GitHub Actions workflows: `agents-governance.yml`, `ci.yml`, `ci-quality.yml`, `ci-report.yml`, `ci-tests.yml`, `deploy.yml` (the Quarto → Cloudflare Pages deploy that this task **deletes**), and `release-please.yml`. All except `deploy.yml` remain untouched.

### 3. Build the `sync-docs.mjs` content-derivation script

**Create `website/scripts/sync-docs.mjs`**. This is the single mechanism that turns canonical markdown in `docs/` into Starlight-compatible content under `website/src/content/docs/synced/`.

The script must:

1. Read this allow-list of source files (everything else in `docs/` is skipped):

   ```
   docs/ARCHITECTURE.md
   docs/RUNBOOK.md
   docs/TESTING.md
   docs/GUARDRAILS.md
   docs/DEPLOYMENTS.md
   docs/EXIT_CODES.md
   docs/adr/*.md
   ```

2. For each file:
   - Parse the **first H1** as `title:` (strip the `# ` prefix). If no H1 exists, fail with a clear error.
   - Parse the **first non-empty, non-heading paragraph** as `description:` (truncate to 160 chars on a word boundary).
   - Strip the leading H1 line from the body (Starlight renders the title from frontmatter).
   - Compute the destination slug: top-level files → `synced/<slug>.md` where slug is the lowercased filename minus extension and with underscores replaced by hyphens. ADRs → `synced/adr/<slug>.md` with the same rule.
   - Write the file with YAML frontmatter:

     ```yaml
     ---
     title: "<derived title>"
     description: "<derived description>"
     editUrl: "https://github.com/Abstract-Data/mediaite-ghostink/edit/main/<original-path>"
     ---
     ```

3. Rewrite internal markdown links inside the body:
   - `](docs/foo.md)` → `](/synced/foo/)` (only for files in the allow-list).
   - `](../adr/ADR-001-foo.md)` → `](/synced/adr/adr-001-foo/)`.
   - Links to files **not in the allow-list** (e.g. `docs/NOTES.md`, `docs/plans/`) are rewritten to absolute GitHub URLs: `https://github.com/Abstract-Data/mediaite-ghostink/blob/main/docs/NOTES.md`.
   - Links to repo root files (`README.md`, `CONTRIBUTING.md`, `AGENTS.md`, etc.) are rewritten to absolute GitHub URLs.
   - Links to `_quarto.yml`, `index.qmd`, `notebooks/`, `pyproject.toml`, `config.toml`, `.github/workflows/*` → absolute GitHub URLs.

4. Print a summary at the end: number of pages emitted, list of any links that could not be rewritten (for manual review).

5. Exit 0 on success, 1 on any error (missing H1, write failure, etc.).

Use only Node built-ins plus a tiny YAML serializer (e.g. write the frontmatter manually — do not add a heavy dependency).

The script is invoked from `package.json` and from CI. It must be **idempotent**: re-running on a clean tree produces no diffs.

### 4. Build the CLI documentation generator

**Create `scripts/generate_cli_docs.py`** (at the repo root, not under `website/`). This Python script walks the Typer app at `src/forensics/cli/__init__.py:main` and emits one Markdown file per command into `docs/cli/`.

Approach:

1. Import the Typer `app` object directly. Use Typer's introspection (`app.registered_commands`, `app.registered_groups`) to enumerate all commands and subcommands.
2. For each command, render Markdown with:
   - H1 of the command name.
   - The command's docstring as the first paragraph (description).
   - A `## Usage` section containing the synopsis line.
   - A `## Options` section listing each option with name, type, default, and help text.
   - A `## Examples` section if the docstring contains fenced code blocks.
3. Write to `docs/cli/<command-slug>.md`. Index page at `docs/cli/index.md` lists all commands with a one-line summary each.
4. The script is idempotent and exits 0 on success.

The `sync-docs.mjs` script must also pick up `docs/cli/*.md` and copy them into `website/src/content/docs/cli/` with frontmatter injection — the same allow-list and rewriting logic applies. (The Starlight sidebar autogenerates this section from `cli/`.)

Run path:

```bash
uv run python scripts/generate_cli_docs.py --out docs/cli
```

Add a Makefile target (append to existing `Makefile`):

```makefile
.PHONY: docs-cli
docs-cli:
	uv run python scripts/generate_cli_docs.py --out docs/cli

.PHONY: docs-dev
docs-dev: docs-cli
	cd website && npm install && npm run dev

.PHONY: docs-build
docs-build: docs-cli
	quarto render --output-dir website/public/report
	cd website && npm install && npm run build
```

### 6. Use Starlight's component library and configuration reference

**Required reading before authoring any MDX page or editing `astro.config.mjs`:**

- [Starlight components overview](https://starlight.astro.build/components/using-components/) — how to import and use built-in components in `.mdx` files, including the import path (`@astrojs/starlight/components`) and the MDX-vs-Markdown distinction.
- [Starlight configuration reference](https://starlight.astro.build/reference/configuration/) — the canonical schema for everything passed to the `starlight()` integration call (`logo`, `social`, `editLink`, `lastUpdated`, `pagination`, `sidebar` group/`autogenerate`/`items`/`attrs`/`badge` schema, `head`, `customCss`, `components` overrides). The example `astro.config.mjs` in step 2 uses these knobs correctly, but if you need to add or change a knob, read the reference page first — it is the source of truth.

**Built-in components available** (all imported from `@astrojs/starlight/components`):

| Component | When to use |
|-----------|------------|
| `Card`, `CardGrid`, `LinkCard` | Landing-page navigation tiles. Already used in `index.mdx`. |
| `Tabs`, `TabItem` | Side-by-side examples — e.g. shell vs. Python API on a CLI page, or `make` target vs. raw command on the quickstart. |
| `Steps` | Numbered procedures. Wrap the quickstart sequence in `getting-started.mdx`. |
| `Aside` | Callouts. Variants: `note`, `tip`, `caution`, `danger`. Use for the corpus-custody and preregistration callouts on the runbook landing, the "do not commit build artifacts" reminder, and any cross-link to `/report/`. |
| `Code` | Syntax-highlighted snippets that aren't a fenced markdown block (dynamically-titled or programmatically-rendered code). |
| `FileTree` | Directory-layout visualizations. Use in `getting-started.mdx` to show the project layout, replacing any ASCII tree. |
| `Badge` | Inline status markers. Already used in the sidebar via `attrs.badge`; the same `Badge` component is documented at the components page for use inside MDX. |
| `Icon` | Inline icons next to headings or list items. |

**Required component usage on hand-authored pages:**

- `website/src/content/docs/getting-started.mdx` MUST use at least one each of: `<Steps>`, `<Aside>`, `<FileTree>`, and `<Tabs>`. The `<Tabs>` block should compare a `make` target with the raw underlying command for at least one quickstart action.
- `website/src/content/docs/index.mdx` MUST use at least one each of: `<CardGrid>`, `<LinkCard>`, and `<Aside>`. The "Forensic report" callout in the example block in step 5 uses `<Card>` — switch it to `<Aside variant="note">` so screen readers announce it as the callout it is.

**Component usage on synced pages:** the `sync-docs.mjs` script does NOT inject components into synced markdown — synced pages remain plain `.md`. If a synced page would benefit from a `<Steps>` or `<Aside>` block, that's a sign the source `docs/*.md` file should be edited (canonical source) rather than the synced copy. Do not edit synced output.

**MDX vs. Markdown:** synced pages and CLI-reference pages are plain `.md` (no component imports). Hand-authored pages are `.mdx`. Promoting CLI-reference pages to `.mdx` with `<Tabs>` for shell vs. Python examples is a v0.2.0 enhancement; do not do it in v0.1.0.

**Mermaid blocks** are rendered automatically by the `rehype-mermaid` plugin configured in step 2. Use a fenced ` ```mermaid ` block in any markdown or MDX page; no component import is needed. The five existing mermaid blocks in `README.md` are not affected (README is not imported into Starlight).

**Configuration knobs in scope for v0.1.0** (all documented at the configuration reference page above): `title`, `description`, `logo` (`light` + `dark` + `replacesTitle`), `favicon`, `social[]`, `editLink.baseUrl`, `lastUpdated`, `pagination`, `sidebar` (manual `items` with `link`/`label`, `autogenerate` for the `cli/` and `synced/adr/` directories, `attrs` and `badge` on the Forensic report entry), `customCss`, `head` (single robots meta tag). Out of scope for v0.1.0: `defaultLocale`, `locales` (i18n), `expressiveCode` overrides, custom `components` slot replacements, and `plugins`. If a future need requires any of those, that is a v0.2.0+ change.

### 8. Replace the existing deploy workflow

**Delete `.github/workflows/deploy.yml`** in this same change. Do this with `git rm .github/workflows/deploy.yml` and commit the deletion. The Cloudflare Pages project becomes orphaned; the maintainer retires it manually outside CI (surface this as a checklist item in the HANDOFF block).

**Create `.github/workflows/deploy-docs.yml`**:

```yaml
name: Deploy Docs
on:
  push:
    branches: [main]
    paths:
      - "website/**"
      - "docs/**"
      - "notebooks/**"
      - "_quarto.yml"
      - "index.qmd"
      - "src/forensics/cli/**"
      - "scripts/generate_cli_docs.py"
      - ".github/workflows/deploy-docs.yml"
  pull_request:
    paths:
      - "website/**"
      - "docs/**"
      - "notebooks/**"
      - "_quarto.yml"
      - "index.qmd"
      - "src/forensics/cli/**"
      - "scripts/generate_cli_docs.py"
      - ".github/workflows/deploy-docs.yml"
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true
      - uses: astral-sh/setup-uv@v5
      - name: Sync Python env
        run: uv sync
      - uses: quarto-dev/quarto-actions/setup@v2
      - name: Generate CLI docs
        run: uv run python scripts/generate_cli_docs.py --out docs/cli
      - name: Render Quarto report
        run: quarto render --output-dir website/public/report
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: website/package-lock.json
      - name: Install website deps
        working-directory: website
        run: npm ci
      - name: Build Astro Starlight
        working-directory: website
        run: npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: website/dist

  deploy:
    needs: build
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

The `pull_request:` trigger runs the `build` job but the `deploy` job is gated to `push` on `main`, so PRs validate the build without publishing.
